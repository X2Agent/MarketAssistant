### 2.2 聚合器加固（commit `5c876e3`）

`AnalysisAggregatorExecutor` 有 ±89 行的实质重构：

#### 改进：expectedCount 从 State 移到构造参数

```csharp
// 旧：从 WorkflowState 读取（跨 SuperStep 时序竞态）
var expectedCount = await context.ReadStateAsync<int>(
    WorkflowStateKeys.ExpectedAnalystCount, ...);

// 新：构造函数直接传入
public AnalysisAggregatorExecutor(int expectedAnalystCount, ...)
```

消除了通过 Workflow State 传递期望计数带来的跨 SuperStep 时序竞态。

#### 改进：失败消息分离

```csharp
// 新增 _failedMessages 列表，失败标记不再混入分析师载荷
if (AnalystFailureMessages.IsFailureMarker(message.Text))
{
    CollectMessage(_failedMessages, message, expectedCount);
    continue;
}
```

失败分析师的消息被分离到独立列表，最终以 `[MISSING_DIMENSION_NOTE]` 系统提示形式附加给 Coordinator，而非混入正文。

#### 改进：诊断日志增强

新增非分析师消息过滤日志、批次计数日志、最终消息诊断日志，便于定位 barrier 消息丢失。

### 2.3 Coordinator 加固（commit `710a356`）

`CoordinatorExecutor` 有 ±79 行变更：

- 新增 `Stopwatch` 耗时计量
- 新增输入/输出消息诊断日志（`LogMessageDiagnostics`）
- 新增 JSON 解析失败时的详细错误日志（文本长度、Content 类型、前 500 字符预览）
- 保留 `YieldOutputAsync` 显式调用（MAF `WithOutputFrom` auto-yield 在流式路径的时序缺陷仍存在）

## 3. P0 问题逐项核查

### P0-1: MAF Fan-In Barrier 消息丢失

#### 状态：⚠️ 根因未修复，workaround 已加固

| 检查项 | 结果 | 证据 |
|--------|------|------|
| MAF 版本 | 1.13.0 → 1.17.0 | `Directory.Packages.props` |
| E2E 测试（无重试） | ❌ 3 个稳定失败 | `MarketAnalysisWorkflowTest` 3 个 `TestCategory("E2E")` |
| 降级测试（有重试） | ✅ 5 轮全通过 | `MarketAnalysisDegradationTest`，`maxAttempts=5/3` |
| 测试重试循环 | 仍在 | L36: `const int maxAttempts = 5` |
| 测试注释版本号 | **过时** | L33: `1.16.0`，应为 `1.17.0` |
| `CoordinatorExecutor.YieldOutputAsync` | 仍在 | L201: 注释 `WithOutputFrom 的 auto-yield 在 RunStreamingAsync 存在时序缺陷` |
| `AggregatorExecutor` 静默返回 | 仍在 | `collected+failed < expected` 时 return |

#### 根因分析

MAF 的 `AddFanInBarrierEdge` 在分析师输出分属不同 superstep 时，barrier 释放后到达的消息被丢弃。`AnalysisAggregatorExecutor` 收到的消息数少于 `expectedCount` 时静默返回，不发送给 Coordinator，事件流无声终止。

#### 现有缓解措施

| 措施 | 位置 | 改进状态 |
|------|------|----------|
| `WithFailureIsolation` | 分析师包装 | 无变化 |
| `_sentToCoordinator` 锁 + Author 去重 | Aggregator | 无变化 |
| `expectedCount` 构造参数传入 | Aggregator | **改进**（从 State 移到构造参数） |
| 失败消息分离 | Aggregator | **新增**（`_failedMessages` 独立列表） |
| `YieldOutputAsync` 显式调用 | Coordinator | 无变化 |
| 终态检测 + `FriendlyException` | Workflow | 无变化 |
| 测试级有界重试 | 测试 | 无变化 |

#### 结论

MAF 1.13.0 → 1.17.0 的升级**未修复 Fan-In barrier 的时序性消息丢失缺陷**。现有 workaround 通过 `expectedCount` 构造参数化和失败消息分离得到了加固，但根因仍在。测试注释中的版本号 `1.16.0` 已过时，应更新为 `1.17.0`。

#### 建议

1. 将测试注释版本号更新为 `1.17.0`
2. 在 Aggregator 内增加超时+降级发送机制：`collected+failed < expected` 时等待有限时间后降级发送已有结果
3. 关注 MAF 后续版本 changelog 中是否提及 Fan-In barrier 修复
4. 长期考虑替换工作流拓扑（与 P0-2 文件系统方案天然契合）

### P0-2: Agent 结果通过对话历史传递

#### 状态：❌ 无变化

| 检查项 | 结果 |
|--------|------|
| `CoordinatorExecutor` 输入方式 | `List<ChatMessage>` 全文本拼接 |
| `session` 参数 | `null`（无状态一次性调用） |
| Token 成本 | 5 位分析师约 5-15 KB/次 |
| 文件系统引用机制 | 未实现 |
| `IAnalysisResultStore` | 不存在 |

#### 当前数据流

```
AnalystAgent (StructuredOutputOptions 产出结构化结果)
  → 输出文本作为 ChatMessage 进入工作流消息流
  → AnalysisAggregatorExecutor 收集 ChatMessage
  → CoordinatorExecutor 拼接为 List<ChatMessage> + 过滤 FunctionCallContent
  → Coordinator.RunAsync(messages, session: null) — 完整文本进 prompt
```

#### 可复用的现有基础设施

| 设施 | 路径 | 可复用性 |
|------|------|----------|
| `ReportArchiveService` | `Services/Archive/ReportArchiveService.cs` | SQLite 持久化，模式可参考 |
| `AnalysisReportCache` | 内存缓存 | 太轻量 |
| `LocalImageStorageService` | `Rag/Services/` | **最佳模式参考**：GUID 文件名、目录隔离、安全校验 |

#### 建议方案

新增 `IAnalysisResultStore`（文件系统实现），分析师写结果到 `{analysisDir}/{runId}/{analystName}.json`，工作流消息只传 `[ANALYST_REF]` 轻量引用，Coordinator 从 store 加载类型化输入。

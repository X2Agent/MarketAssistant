## 0. 分支与执行约定

当前工作区在 `feature/multi-provider-support` 上，且存在未提交改动。重构**不要**叠在脏工作树上。

```text

4. git checkout -b refactor/p0-p1-correctness
```

- 不在 ViewModel 或业务服务里手写新的 retry、缓存、搜索框架。
- 提交信息遵循 `[模块] 变更概要`。

## 2. P0 详解

### P0-01 检索距离方向

**现象：** 知识库开启时，最相关段落可能被去重丢掉或排到后面。协调分析师和追问对话都走 `GroundingSearchTools` → `IRetrievalOrchestrator.RetrieveAsync`。

**根因：**

1. `TextParagraph.TextEmbedding` 配置 `DistanceFunction.CosineDistance`。在当前 `Microsoft.SemanticKernel.Connectors.SqliteVec 1.74.0-preview` 下，`VectorSearchResult.Score` 应按距离解释：越小越相关。
2. 去重保留最大值：`RetrievalOrchestrator` 中 `OrderByDescending(x => x.VectorScore).First()`。
3. 重排把最大值归一成最高相关：`RerankerService` 中 `(item.VectorScore - minScore) / range`。
4. 异常回退也按降序。
5. 类型名和注释仍写“向量相似度分数”（`ScoredSearchResult.VectorScore`），后续改动容易继续用错。

**方案：**

1. `ScoredSearchResult.VectorScore` 重命名为 `VectorDistance`。接口注释改为距离语义。
2. 去重保留最小距离：`.OrderBy(item => item.VectorDistance).First()`。
3. 归一化改为距离反转：

```csharp
var normalizedSimilarity = range < 1e-9
    ? 1.0
    : (maxDistance - item.VectorDistance) / range;
```

4. 异常回退按距离升序。
5. 日志字段用 `distance` / `similarity`，禁止再统称 `score`。
6. **不要**同时改 0.6/0.2/0.1/0.1 权重。**不要**用 `1 - distance` 并假设结果在 `[0,1]`。
7. 升级 SqliteVec 时必须重测 Score 语义，不能只看属性名。

**改哪些文件：**

- `src/MarketAssistant.Rag/Interfaces/IRerankerService.cs`
- `src/MarketAssistant.Rag/Services/RetrievalOrchestrator.cs`
- `src/MarketAssistant.Rag/Services/RerankerService.cs`
- `tests/Vectors/RerankerServiceTest.cs`
- `tests/Vectors/RetrievalOrchestratorIntegrationTest.cs`

**测试：**

- 距离 0.1 必须排在 0.8 前。
- 同一段落被多个改写查询命中时保留最小距离。
- 所有距离相同时顺序稳定。
- Reranker 抛错时仍按距离升序。
- 一条 SQLiteVec 集成测试：两个可控向量，断言连接器返回顺序与距离含义。

**完成标准：** 链路中不再把 `CosineDistance` 当越大越好；`VectorScore` 命名从该链路消失。

### P0-02 文本向量维度无校验

**现象：** 用户换成非 1024 维 Embedding 模型后，写入或检索失败，错误难以对应到“维度不匹配”。

**根因：** `RagConstants.EmbeddingDimension = 1024`，`[VectorStoreVector]` 把维度写死在 schema。`RagIngestionService` 把 `GenerateAsync` 的结果原样赋给 `TextEmbedding`，没有检查 `Vector.Length`。截断/补零只发生在 CLIP 图像路径。第一阶段**不要**做动态多维度。

**方案：**

1. 生成向量后、`UpsertAsync` 前校验：
   - `embeddings.Count == paragraphList.Count`
   - 每个 `embeddings[i].Vector.Length == RagConstants.EmbeddingDimension`
2. 不匹配则该块失败，不写入，错误消息面向用户：

```text
Embedding 维度不匹配。当前知识库只支持 1024 维，实际为 {actual}。
请改回支持的 Embedding 模型，或重建向量库后再切换。
```

3. 不记录 API Key、全文、完整向量。
4. 更换模型/维度的产品语义：必须重建 Collection，而不是静默截断。

**改哪些文件：** `RagIngestionService`、`IRagIngestionService`（与 P0-03 一起改返回值）、摄取测试。

**测试：** 1024 维写入成功；1536 维在第一次 Upsert 前失败；返回条数少于文本条数时失败。

### P0-03 块失败被报告为文件成功

**现象：** 文档只有部分块入库，设置页仍增加成功计数并提示“全部完成”。

**根因：**

1. `RagIngestionService.IngestWithBlocksAsync` 对每个 block `catch (Exception)` 只打 Warning，方法正常返回。
2. `IRagIngestionService.IngestFileAsync` 无返回值、无 `CancellationToken`。
3. `SettingsPageViewModel` 只要 `await IngestFileAsync(...)` 不抛，就 `successCount++`。
4. `OperationCanceledException` 若被块级 catch 吃掉，取消会变成“部分成功”。

**方案：**

```csharp
public sealed record RagIngestionFailure(
    int BlockOrder,
    string ErrorCode,
    string Message);

public sealed record RagIngestionResult(
    int BlockCount,
    int ParagraphCount,
    IReadOnlyList<RagIngestionFailure> Failures)
{
    public bool IsSuccess => Failures.Count == 0 && ParagraphCount > 0;
    public bool IsPartialSuccess => ParagraphCount > 0 && Failures.Count > 0;
    public bool IsFailure => ParagraphCount == 0;
}
```

接口改为：

```csharp
Task<RagIngestionResult> IngestFileAsync(
    VectorStoreCollection<string, TextParagraph> collection,
    string filePath,
    IEmbeddingGenerator<string, Embedding<float>> embeddingGenerator,
    CancellationToken cancellationToken = default);
```

规则：

- `OperationCanceledException` 必须继续抛出。
- 其余块异常记入 `Failures`，可继续后续块。
- 无 reader / 零块：返回失败，不要假装成功。
- UI 三态：成功 / 部分成功 / 失败。部分成功不得计入“完全成功”。提示里给出失败文件和失败块数。

**改哪些文件：**

- `IRagIngestionService.cs`、`RagIngestionService.cs`
- `src/MarketAssistant.App/ViewModels/SettingsPageViewModel.cs`（向量化循环，约 `successCount` 逻辑）
- `tests/Vectors/RagIngestionServiceIntegrationTest.cs` 及新增单元测试

**本项与 P0-02 同一提交：** 摄取接口只改一次，避免调用方改两轮。

### P0-04 按市场裁剪分析师

**现象：** A 股和虚拟币共用五位分析师。财务分析师提示词是“财务报表、ROE、现金流”；币圈却把 `IFinancialTools` Keyed 到 `CryptoMetricsTools`。角色能跑，语义被拉歪，评分维度对加密资产不诚实。

**根因：**

1. `GetEnabledAnalysts()` 只看 `UserSetting.EnabledAnalystRoles` 和 `[RequiredAnalyst]`，不看 `MarketType`。
2. `[RequiresTools(typeof(IFinancialTools))]` 在两个市场都能解析到实现，所以工厂不会失败。
3. 设置页加载全部具体分析师类型，没有按当前市场过滤。
4. 只有一份 `FinancialAnalyst.yaml`。

**方案：**

1. 新增 `[SupportedMarkets(params MarketType[] markets)]`。缺省表示两个市场都支持（基本面、技术、情绪、新闻、协调器）。
2. `FinancialAnalystAgent` 标记仅 `MarketType.AShare`。
3. 新增 `CryptoMetricsAnalystAgent`（显示名如“项目指标分析师”），`[RequiresTools(typeof(ICryptoMetricsTools))]`，仅 `MarketType.Crypto`，独立 YAML（市值、换手、资金费率、持仓量等，不要套财报词）。
4. `GetEnabledAnalysts()` 增加：类型必须支持 `_marketContext.CurrentMarket`。
5. 设置页 `LoadAnalystRoles()` 按当前市场列出；切换市场时刷新。用户在 A 股关掉的角色不要误伤币圈名单——`EnabledAnalystRoles` 的 key 继续用类型名即可，因为两个市场的类型名将分开。
6. `AnalysisCacheService` 若把启用角色纳入缓存键，必须包含市场类型，避免串缓存。
7. 不要在本项改评分公式或协调器 schema。`CoordinatorResult.DimensionScores` 若仍有“财务面”字段：A 股填财务，币圈填项目指标，并在协调器提示词里写清映射，避免模型用“财报”字样描述代币。

**改哪些文件：**

- `src/MarketAssistant.Agents/Analysts/Attributes/`（新特性）
- `FinancialAnalystAgent.cs`、新建 `CryptoMetricsAnalystAgent.cs`
- `src/MarketAssistant.App/config/prompts/CryptoMetricsAnalyst.yaml`
- `MarketAnalysisWorkflow.GetEnabledAnalysts`
- `SettingsPageViewModel.LoadAnalystRoles`
- `AnalystAgentFactoryTest`、工作流相关测试
- `src/MarketAssistant.App.Services/AGENTS.md` / `Agents/AGENTS.md` 各补一句：分析师必须声明支持的市场

**测试：**

- Crypto 下创建的分析师列表不含 `FinancialAnalystAgent`，含新指标分析师。
- AShare 相反。
- `[RequiredAnalyst]` 仍强制启用，但也要受市场过滤（协调器两边都支持）。
- 设置页在切换市场后角色列表变化。

**完成标准：** 币圈分析运行时不再出现“财务报表分析师”执行器。

### P0-05 分析质量最小评估骨架

**现象：** 主线“值不值得信”无法验证。现有测试覆盖工作流身份、失败隔离、聚合器，但不覆盖“同一标的、固定数据下报告是否稳定、缺数据是否降级”。

**根因：** 评分来自 LLM 自评；Tool 走真实 HTTP；没有冻结的工具响应夹具，也没有“无答案 / 缺数据”断言。

**方案（骨架，不是大规模评测平台）：**

1. 新增 `tests/Evaluation/`（或 `tests/Analysis/Golden/`），默认不打真实模型。
2. 第一期只锁定**编排契约**，用假 Tool / 假 ChatClient：
   - 全部分析师成功 → 聚合器发给协调器的消息数 = 成功数 + 1 条维度缺失说明（失败为 0 时说明可空）。
   - 部分失败 → 协调器收不到失败标记原文，只收到缺失说明。
   - 全部失败 → 不派发协调器，工作流给出明确错误。
   - 结构化输出反序列化失败 → 计入降级，不把半截 JSON 当报告。
3. 准备 5～10 个离线夹具（A 股 1 只、币 1 个交易对即可）：冻结的行情/财务 JSON + 期望字段“必须出现数据缺失声明 / 不得出现编造 PE”。
4. 可选：环境变量开启的 live 评估，失败不算 CI 红（与 RAG 集成测试缺 `JINA_API_KEY` 同一策略）。
5. **不要**在本项训练提示词或调温度。评估是尺子，不是优化器。

**改哪些文件：** 现有 `AnalysisAggregatorExecutorTest`、`MarketAnalysisDegradationTest` 可扩展；新增 golden 夹具与 README（测试目录内短说明即可，不另开设计文档）。

**完成标准：** 一条本地命令能跑编排契约；缺数据路径有断言；live 评估缺密钥时跳过而不是删断言。

## 3. P1 详解

### P1-01 稳定 Key 与文档级替换

**现象：** 同一文件再向量化，旧段落仍能召回；同一文档两个同级同名标题，后写覆盖先写。

**根因：**

1. 摄取只有 `UpsertAsync`，没有按文档删除过期 Key。
2. 标题键：`{fileHash}:hdg:{level}:{contentHash[..8]}`，不含全局 `Order`。列表/表格/图片同样。
3. `fileHash` 来自路径字符串哈希，不是稳定 `DocumentId`（大小写、分隔符、相对路径会变）。

**方案：**

Key 统一为：

```text
{documentId}:{blockKind}:{order:D6}:{contentHashPrefix}
```

`DocumentId`：`Path.GetFullPath` → 统一分隔符 → Windows 大小写不敏感 → 哈希。不要把明文路径放进 Key，也不要用全文当文档身份。

文档级替换语义：

```text
解析并生成新段落
  -> 维度与数量校验（P0-02）
  -> 写入 newKeys
  -> 删除 oldKeys.Except(newKeys)
  -> 成功后再更新文档清单
```

引入 `IRagDocumentCatalog`（清单持久化先评审：优先 SQLite 旁路表或现有 VectorStore 数据字段，**禁止**在业务服务手写 FTS5/SQL 拼搜索）。清单至少含：CollectionName、DocumentId、DocumentUri、内容哈希、当前 Key 集合、Embedding 模型标识、维度、更新时间。

失败恢复：写入成功但清单失败时，下次摄取必须能重新收敛。删除文档要有服务入口：按清单删记录再删清单。

**测试：** 同一文件摄取两次记录数不增长；删一段落后旧段不可召回；两个同名标题都在且 Key 不同；内容不变可幂等；删除文档后不可召回。

**完成标准：** 文档更新后库中无旧块；合法重复块不互相覆盖。

本项会改变存量 Key → **重建 Collection**，不要写迁移脚本猜旧键。

### P1-02 检索保留元数据与邻接上下文

**现象：** `Order`、`Section`、`PublishedAt`、`BlockKind` 摄取时写了，检索后立刻丢掉。时效评分只能从 URL/正文猜时间。表格命中没有表头/前后文。

**根因：** `RetrievalOrchestrator` 在合并阶段就构造 `TextSearchResult`（Name/Link/Value），后续 `IRerankerService` 只看得见这三字段。

**方案：**

内部模型：

```csharp
public sealed record RagSearchCandidate(
    TextParagraph Record,
    double VectorDistance,
    string MatchedQuery);
```

- 公开 `IRetrievalOrchestrator.RetrieveAsync` 仍可返回 `TextSearchResult`，转换放在**最后一步**。
- `IRerankerService` 入参改为 `RagSearchCandidate`。
- 去重优先 `Record.Key`，其次 `ContentHash`。
- 时效优先 `PublishedAt`，缺失再猜 URL/正文。
- 新增 `IContextExpansionService`：按 `DocumentId + Order` 取命中块前 1 后 1；同 Section 优先；跨文档或跨主 Section 停止；总 token 上限；重叠窗口去重。表格优先补最近标题；标题优先补后一个正文。

**测试：** 元数据在重排前后不丢；不跨 `DocumentUri`；不跨主 Section；扩展后不超过上限。

**完成标准：** 内部链路不以 `TextSearchResult` 当核心模型。

### P1-03 图片能力收敛

**现象：** 注释/常量仍写“跨模态”“文本与图像统一维度”。检索只搜 `TextEmbedding`。CLIP 失败时 `HashToVector` 仍生成 1024 维向量。普通文本块还写入全零 `ImageEmbedding`。

**根因：** 维度相同被当成语义空间相同。哈希向量有确定性、无语义。连接器可能不允许空向量字段，代码用零向量“保证不为 null”。

**方案：**

1. 产品与注释统一为：**图片说明（Caption）的文本检索**。在 `RagConstants`、`TextParagraph`、`RagIngestionService`、设置页文案中改名。
2. CLIP 失败：不生成可检索哈希向量；图像向量标记不可用；Caption 成功则仍可靠文本向量召回。
3. 评估 `ImageEmbedding` 消费者：检索不用就停止写入；若连接器要求非空，用明确的 Unavailable 标记，禁止把哈希向量当语义。
4. 只有同时具备 CLIP 文本塔查询、融合测试通过后，才允许恢复“跨模态”一词。

**测试：** 无 CLIP 模型时不产生哈希语义向量；Caption 成功可被文本检索命中；Caption 与 CLIP 都失败时摄取结果含失败信息。

### P1-04 RAG 离线评估最小集

**现象：** Vectors 测试再绿也无法回答“修距离之后检索是变好还是变差”。

**方案：**

- 首版 10～20 条即可（报告写 30～50 是目标态，本轮不追求）。
- 覆盖：同义改写、股票代码/数值、表格、无答案、图片 Caption（若有样本）。
- 指标：Recall@1/3/5、MRR、无答案误召回、P50/P95。二元标签阶段不上 nDCG。
- 每条记录：代码版本、Embedding 模型与维度、数据集版本、失败查询列表。
- 命令可重复；缺 `JINA_API_KEY` 时标记环境阻塞，不删断言。

前置：P0-01 已合入，否则基线本身是反的。

### P1-05 A 股 HTTP 下沉到 DataProviders

**现象：** `MarketAssistant.DataProviders` 只有 Binance/CoinGecko/CoinDesk。A 股 Tool 和业务服务直接 `CreateClient("Cls"|"ZhiTu"|"EastMoneySearch")`。

**根因：** 币圈接入先独立成库，A 股调用留在 `App.Services`。Keyed Tools 需要数据，就地写了 HTTP。

**当前散落点：**

| 调用方 | 命名客户端 |
|---|---|
| `AShareBasicTools` | Cls、ZhiTu |
| `AShareFinancialTools` / `Technical` / `Sentiment` | ZhiTu |
| `AShareNewsTools` | EastMoneySearch |
| `AShareAssetInfoService` | Cls |
| `AShareKLineService` | ZhiTu |
| `PriceAlertService`（A 股报价） | Cls |

**方案：**

1. 在 `DataProviders` 增加 A 股客户端（按源拆类型，不要一个上帝类）：
   - `ClsQuoteClient`：行情/搜索
   - `ZhiTuMarketClient`：K 线、财务、技术、情绪
   - `EastMoneyNewsClient`：新闻搜索
2. 反序列化模型放 DataProviders；跨模块 DTO 若已被 Tool 契约使用，留在 `Agents/Tools/Models/AShare`，客户端映射过去。
3. 错误继续包装 `FriendlyException`。Token 仍从 `IUserSettingService` 注入，禁止写进仓库。
4. HttpClient 命名注册可以暂时留在 `App.Services` 的 `AddBusinessServices`（宿主才有完整 Http 弹性管线）。DataProviders 通过 `IHttpClientFactory` + 现有名字消费。若要更干净，可把 `AddAShareDataProviders(this IServiceCollection)` 放在 DataProviders，由 `AddBusinessServices` 调用。
5. Tool / AssetInfo / KLine / PriceAlert **删除**直接 `GetStringAsync` + 手解析，改为调客户端。
6. 更新 `src/MarketAssistant.DataProviders/AGENTS.md`：本层同时覆盖加密货币与 A 股外部 API。

**测试：** 现有 Tool 测试改为 mock 新客户端或继续 mock `HttpMessageHandler`；每个客户端至少一条反序列化容错（`--`、null、字符串数字）。

**非目标：** 换官方行情源、加 WebSocket 实时。

### P1-06 交易产品口径与入口

**现象：** README“主要功能”写了自主交易；`MainWindowViewModel.RebuildNavigationItems` 用 `#if DEBUG` 包住交易页。Release 用户按文档会认为功能存在。引擎、风控、人工确认（`RiskConfig.RequireConfirmation`、`TradeConfirmationService`）其实已经有。

**根因：** 交易实现按实验室功能合入，文档按完整产品宣传；用编译符号隐藏入口，而不是产品开关。

**方案（本轮选口径，不把交易做成券商级产品）：**

推荐默认：**实验功能**。

1. README 交易一节改为“实验功能，默认关闭；Debug 或设置中显式开启后可见”。
2. 去掉 `#if DEBUG`，改为 `UserSetting.EnableExperimentalTrading`（默认 false）。仅当当前市场 `SupportsTrading` 且该开关为真时显示导航。
3. 设置页增加开关 + 风险说明（实盘、密钥、无法撤销等）。
4. 不在本项扩展策略类型或交易所。
5. 若产品决定“Release 也作为主功能交付”，则同一 PR 必须包含：默认确认阈值不可关死、失败策略已有测试的回归清单、README 与关于页同步。二者选一，禁止第三种（文档写有、入口没有）。

**改哪些文件：** `MainWindowViewModel`、`UserSetting`、设置页、`README.md`。

**测试：** 开关关闭时导航无交易；Crypto + 开关打开时有；A 股即使打开开关也无（`SupportsTrading == false`）。

### P1-07 分析师产物改为引用传递

**现象：** `AnalysisAggregatorExecutor` 把每位分析师的完整文本 `SendMessageAsync` 给 Coordinator。五份结构化 JSON 进一次上下文，Token 贵、易截断、易失真。追问侧 `MarketChatSession` 也会把分析消息拼进 `_analysisContext`。

**根因：** Fan-In 最省事的契约是 `List<ChatMessage>`。归档（`ReportArchiveService`）发生在工作流结束之后，协调阶段用不上。

**方案：**

1. 聚合器在收齐后：将每份分析师文本写入本次 Run 的产物存储（复用归档 SQLite 或 `IAnalysisCacheService` 旁路表），key = `{runId}/{analystName}`。
2. 发给 Coordinator 的消息改为短摘要：分析师名、评分/评级（若已结构化）、产物 key、字符数。另附一条系统说明：必须通过工具读取产物全文，禁止凭摘要编造细节。
3. 给协调器增加只读工具 `GetAnalystArtifactAsync(runId, analystName)`，只允许读本次 Run。
4. 追问会话：默认注入摘要 + 工具；用户追问涉及某维度时再拉全文。不要一上来把五份全文塞进 system。
5. 失败分析师仍只传缺失说明，不写空产物冒充成功。

**测试：** 发给 Coordinator 的消息总长度显著小于原文之和；工具能读回原文；错误 runId 拒绝；全部失败仍不派发 Coordinator。

**非目标：** 通用多 Agent 文件系统框架、跨会话记忆重构。

### P1-08 MCP 最小暴露

**现象：** `MCPServerConfig.AllowedTools` 为空时加载该服务器全部工具，只打 Warning。`McpToolContextProvider` 在每次 Chat 调用前把这些工具注入。多服务器时模型会无约束试探。`Category` 字段已有，但加载路径未按分类限制。

**根因：** 白名单是可选的；空列表被实现成“全部允许”，对最小暴露不友好。

**方案：**

1. 空 `AllowedTools` 的默认改为：**不暴露任何工具**，并在 MCP 配置页强制用户勾选。保留“允许全部”需要显式 `AllowAllTools = true`（默认 false），配置页用危险确认。
2. 按 `Category` 过滤：对话会话只注入 `general`/`search`；不要把 `code` 类工具默认给市场分析 Chat。分析工作流默认不注入 MCP（当前协调器只显式加了 `GroundingSearchTools`，保持如此）。
3. 工具名加前缀 `mcp.{serverName}.{toolName}`，降低多服务器重名冲突（若 MAF 工具名允许点号；不允许则用下划线）。
4. 配置页：列出服务器工具，默认全不选；保存时写入 `AllowedTools`。
5. 已有配置迁移：旧配置空白名单且曾经能用 → 启动时记一条警告，本轮不自动 `AllowAllTools=true`（避免 silently 维持过大暴露）。在关于/设置给一次性提示“请重新勾选 MCP 工具”。

**测试：** 空白名单 → 0 工具；`AllowAllTools` 才加载全部；分类过滤生效；过滤审计日志仍记录。

## 5. 验收

P0 全部完成后：

1. CosineDistance 越小的候选不会在去重或重排被降权。
2. 非 1024 维向量在 Upsert 前失败，UI 有可操作说明。
3. 块失败不会显示为文件完全成功；取消不会被当成成功。
4. 虚拟币分析不再运行财务分析师；A 股不再运行币圈指标分析师。
5. 分析编排的成功/部分失败/全失败路径有不依赖真实模型的自动化测试。

P1 全部完成后：

6. 同一文档重复摄取不累积旧块；删除后不可召回；重复标题不互相覆盖。
7. 重排能用 `PublishedAt`；上下文扩展能用 `Order`/`Section`。
8. 对外不再宣称跨模态检索；哈希向量不参与语义排序。
9. 检索策略变更可用最小评估集对比。
10. A 股外部 HTTP 只出现在 DataProviders（或由其注册的客户端）。
11. README 与导航对交易的描述一致。
12. 协调器默认上下文是摘要 + 引用，全文按需读取。
13. MCP 空白名单不再等于暴露全部工具。
